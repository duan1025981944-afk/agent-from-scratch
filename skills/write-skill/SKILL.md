# 写一个技能

技能 = 一个目录 + 一个 `SKILL.md`。frontmatter 给程序看，正文给模型看。

动手前先想清楚两件事：**这件事值得常驻一行清单吗**（每个技能的清单行要占约 30 token），
**它需要的工具本项目有吗**（现在只有 read_file / list_dir / write_file / echo / load_skill，
没有 shell、不能联网——正文里让模型跑命令是写不成的）。

## 硬规矩（违反了会被直接跳过）

1. **frontmatter 的 `name` 必须等于目录名。** 对不上会被跳过并警告，技能等于不存在。
2. **`name` 只能用小写字母、数字、连字符**，不超过 64 字符，不以连字符开头或结尾，不出现连续两个连字符。
3. **`description` 不能为空**，不超过 1024 字符。缺了同样被跳过。
4. **正文不超过 8000 字符。** 超出的部分发给模型时会被截掉尾巴——模型会照着半本手册做事。

## description 怎么写（这一句决定技能会不会被用）

它是唯一常驻系统提示的内容，模型全靠它判断该不该读正文。三件事缺一不可：

- **做什么**：一句话说清能力
- **什么时候用**：写上用户可能说的原话（"退货""到哪了""审一下这个文件"）
- **什么时候不用**：至少一条反例

反例不是客套。没有反例时模型会在不该用的场合也调它，白花一整圈。

```
写得好：按本项目的工程规范审查一个 Python 文件……用户说"审一下 xxx.py"时使用。
        不要用于解释代码在干什么、也不要用于审查本项目之外的代码风格。
写得差：帮助进行代码审查。
```

## 正文怎么写

- 开门见山写**步骤**，不要先铺垫背景——模型读到正文时已经决定要用它了
- 每一步说清**用哪个工具**（例如"先用 read_file 读目标文件"）
- 写上**边界**：什么情况下应该停下来问用户，而不是硬做
- 末尾给一个**输出格式**的样例，模型会照着排版
- 细节不要写进正文，正文只留"怎么做"

**暂时不要依赖 `references/` 附带文件**：本项目的 `load_skill` 只读 SKILL.md，
附带文件要靠 `read_file` 读，而那只在"从仓库目录启动"时才够得着。写不下就精简，别拆。

## 骨架

```markdown
---
name: <目录名>
description: <做什么>。用户说"<原话 1>""<原话 2>"时使用。不要用于<反例>。
---

# <标题>

<一句话说清这是什么场景>

## 步骤
1. 先用 <工具> 做 <什么>
2. ……

## 边界
- <什么情况下停下来问用户>

## 输出格式
<样例>
```

## 写完怎么验

新建 `skills/<名字>/SKILL.md` 之后，让用户在终端跑：

```
python -c "from agent.skills import skill_catalog; print(skill_catalog())"
```

新技能出现在清单里就算合格；**只看到一条警告说明哪条硬规矩没过**，照警告改。

## 边界

- 用户没说要新建技能时，不要擅自创建文件——先说明打算建什么、建在哪，得到同意再动手
- 一个技能只解决一类事。发现正文里在讲两件不相干的事，拆成两个技能

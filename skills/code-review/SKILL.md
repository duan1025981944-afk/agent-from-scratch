# 代码审查

先用 `read_file` 读目标文件，再**逐个维度**过一遍下面七条。

规矩：**只报你能在这个文件里指出来的具体问题**，每条给出「问题在哪一行 / 为什么违反 / 怎么改」。
没问题的维度直接说"这一项没问题"，不要凑数。最后给一句总体判断。

## 1. 分层与依赖

- 看 `import`：这个文件是不是知道了它不该知道的层？（执行层不该 import 存储层；工具层不该 import 上下文层，`load_skill.py` 那处是有注释说明的例外）
- 同一个知识是不是只有一个地方知道？路径、阈值、格式各自只该有一个来源，复制必然漂移。
- 新加的抽象层：它把复杂度**减少**了多少？只是把三行代码换了个名字的"浅模块"不值得存在。

## 2. 错误处理

- 这个错误能不能**被设计掉**？合法输入范围有限时用查表（白名单），比事后检查更省、更不容易写漏。
- 错误文本有没有**反向指路**：告诉调用方下一步该做什么，而不只是"失败了"。
- 启动期的错误要**大声**（缺配置、缺模板直接炸），运行期的错误要**接住**（转成文本交回去，让上层自己决定）。
- 不可逆的动作（写文件、覆盖、删除）：检查必须在动作**之前**。

## 3. 命名与注释

- docstring 是不是四段式：**这是什么 / 不是什么 / 怎么用 / 例子**。
- 注释写的是"为什么这样"还是"这行在干什么"？后者是废话，代码本身已经说了。
- 出现的每个数字（阈值、上限、系数）有没有**出处**：来自实测、文档还是拍脑袋？拍脑袋的要标出来。
- 名字有没有骗人：函数名承诺的事和它实际做的事是不是同一件。

## 4. 测试

- 每个测试的 docstring 末尾有没有写**负对照**（把代码改成什么样，这条必须红）？
- 那个负对照**真的验过**吗？改坏了还绿的测试是假的安全感。
- 断言的是**行为**还是**实现细节**？后者会在重构时误报。
- 测试之间有没有共享可变状态？`tmp_path` 是每个测试独占的，`tmp_path.parent` 不是。

## 5. 数据与不可变性

- 写入是不是只**追加**？回头改写已经落盘的记录，就等于让记账的人改账本。
- 有损的加工（截断、压缩、摘要）是不是只发生在**发送前**，而不是写入前？存档一旦被截，调大阈值也救不回来。
- 覆盖整份文件之前，有没有留下能退回去的快照？

## 6. 变更的代价

- 再加一个同类的东西（一个工具、一个技能、一个 Provider），要改几个文件？答案应该是 1。
- 这次改动会不会**扩散**到多个文件才算完？要改五处的设计，说明这件事没有单一的归属。
- 新增的配置项/参数：有没有默认值，让所有旧调用一个字都不用改？

## 7. 边界与防御

- 外部来的输入（模型给的参数、磁盘上的文件、网络响应）在进入核心逻辑前被约束了吗？
- 路径类参数：有没有**先展开再判断**（`resolve()` 之后再比对），而不是先比字符串？
- 依赖外部服务的调用有没有超时和重试？没有的话，一次 429 就会炸掉整个进程。
- 防御代码有没有**证据**？没量过就加的防御，是在为想象中的问题付真实的复杂度。

## 输出格式

```
## 1. 分层与依赖
✅ 没问题 / ⚠️ 第 42 行：runner.py import 了 session.manager，执行层不该知道存储层
   改法：把会话 key 由 main.py 拼好传进来

...（七个维度逐个）

## 总体
两处要改（②③），其余没问题。最要紧的是第 42 行那条跨层 import。
```

## 范围

只审用户指定的那个文件。需要交叉验证时最多再读一个相关文件，并且**说明为什么要读它**。
不要顺手把整个 tests/ 都读一遍——那会把上下文吃掉，而且大多数结论用不上。

# mini_nanobot 设计文档 · 兼回顾路线图

> 这份文档回答两个问题：**从哪里开始把项目读一遍**（第一部分），
> 以及**为什么每样东西放在它现在的位置**（第二部分）。
>
> 隔一段时间没看、忘了怎么回事 —— 从第一部分按顺序读，一步一验证，
> 大约两三个小时能把整个项目重新装回脑子里。
> 想查某个具体设计的理由 —— 直接翻第二部分对应的小节。
>
> 每个源文件顶部的 docstring 都是那个文件自己的详细说明书（"这个文件是什么 /
> 不是什么 / 怎么用 / 例子"）。本文档不重复它们，只讲**文件之间的关系**和
> **跨文件的规矩**。读到某个文件时，先读它的 docstring，再回来看这里。

## 第一部分 · 回顾路线：一层一层往下读

### 全景图：七层，从外往里

```
                         你敲的字
                            │
   ┌────────────────────────┼────────────────────────────┐
   │ ① 编排层   main.py     │  先做什么、后做什么、怎么打印   │
   └────────────────────────┼────────────────────────────┘
                            │
   ┌────────────────────────┼────────────────────────────┐
   │ ② 执行层   agent/runner.py                           │
   │            调模型 → 要不要用工具 → 执行 → 再调        │
   └──────┬─────────────────┼──────────────────┬─────────┘
          │                 │                  │
   ┌──────┴──────┐   ┌──────┴──────┐   ┌───────┴────────┐
   │ ③ 工具层    │   │ ④ 模型层    │   │ ⑤ 上下文层      │
   │ agent/tools/│   │ providers/  │   │ context/prompts │
   │             │   │ config/     │   │ tokens/payload  │
   │             │   │             │   │ compaction      │
   └─────────────┘   └─────────────┘   └───────┬────────┘
                                               │
   ┌───────────────────────────────────────────┼─────────┐
   │ ⑥ 存储层   session/manager.py → session/messages.py │
   │            → storage/jsonl.py                       │
   └───────────────────────────────────────────┼─────────┘
                                               │
   ┌───────────────────────────────────────────┼─────────┐
   │ ⑦ 记忆层   agent/memory.py                          │
   │            data/memory/MEMORY.md（便利贴）           │
   │            data/memory/history.jsonl（流水账）       │
   └─────────────────────────────────────────────────────┘
```

**读的顺序就是这个编号。** 从外往里：先知道一轮对话的骨架，再看每根骨头。

每一步都有三样东西：**读什么、带着什么问题读、读完怎么验证**。
验证不是可选项 —— 读完没验证，等于没读。

### 第 1 步 · 编排层：`main.py`

**读什么**：先读文件顶部 docstring，再直接跳到 `main()` 函数最后那个 `while` 循环。

**带着什么问题读**

- 一轮对话分几步？每步的先后顺序为什么不能换？
- `boundary` 这个变量是干什么的？为什么必须在压缩**之后**记？
- 系统提示为什么是模块级算一次，而不是每轮算？

**答案的形状**（读完对一下）

```
① compact_if_needed()        超预算才压缩，一轮最多一次（要花钱）
② boundary = len(messages)   ★ 必须在 ① 之后：压缩会让列表变短
③ messages.append(user)
④ runner.run()               转循环
⑤ session.save_turn(messages[boundary:])   只落盘这轮新长出来的
⑥ print                      先落盘再打印
```

`boundary` 记早了（挪到 ① 前面）的后果：边界比压缩后的列表还长，`messages[boundary:]` 切出来是空列表，
**这一轮根本没存进存档，而且不报错**。（这里早先写的是"把旧消息重复写进存档"，拿数字推一遍才发现不对。）

**验证**：用数字推。压缩前 21 条，边界记成 21；压缩后剩 6 条，加上这一轮的一问一答是 8 条；
`messages[21:]` 是 `[]`。不要指望"把 ② 挪到 ① 前面跑一次真对话"能看出问题——
压缩线是 190,000，平时根本不触发，顺序写反了也一切如常，直到真压缩的那一轮悄悄丢掉。

**这一层的规矩**：它只懂顺序。它**不知道**会话存在哪、循环转几圈、系统提示写了什么。

### 第 2 步 · 执行层：`agent/runner.py`

**读什么**：docstring 全文（它把循环的形状画出来了），然后读 `AgentRunner.run()`。

**带着什么问题读**

- 循环里**唯一的分岔点**在哪？
- 为什么 `assistant` 和 `tool` 两条消息都要 append，不能只塞工具结果？
- 工具执行有三种情况（A 工具不存在 / B 参数是坏 JSON / C 正常执行），
  前两种为什么不抛异常、而是转成文字塞回给模型？
- `except asyncio.CancelledError: raise` 为什么必须写在 `except Exception` **前面**？

**答案的形状**

```
for i in range(max_iterations):
    payload = build_payload(messages)     # 加工成这次要发的
    reply = await provider.chat(payload)  # 调模型
    messages.append(reply.raw)            # 模型说的话先入链
    if not reply.wants_tools:             # ★ 唯一的分岔点
        break
    执行每个工具，把结果 append 进 messages
```

模型每次要么"要用工具"（继续转），要么"说完了"（退出）。**没有第三种可能。**

工具报错对模型来说和工具成功是同一件事 —— **都是一段文本**。它读完这段文本自己决定下一步。
抛异常会中断整个循环，Agent 就只剩"成功或崩溃"两条路；转成文本回给它，它能自己换个路径重试。
**这是 Agent 能自愈的根本。**

**验证**：`tests/test_runner.py` 有 6 个测试。读 `test_every_tool_call_is_answered_by_a_tool_role_message`，
然后把 runner 里"情况 A"那段的 `role: "tool"` 改成 `"assistant"`，跑测试，看它红。改回来。

**这一层的规矩**："循环层不碰产品层"。它**不知道** SOUL.md 存在、不知道在调哪家模型、不写盘。
换渠道、换模型、换存储，这个文件一个字都不用改。

### 第 3 步 · 工具层：`agent/tools/`

四个文件，按这个顺序读：

| 顺序 | 文件 | 一句话 | 带着什么问题 |
|---|---|---|---|
| 1 | `base.py` | 一个工具 = 一份说明书 + 一段代码 | `description` 为什么要写"不要用于……"这种反例？ |
| 2 | `loader.py` | 自动登记处 | `importlib.import_module` 和普通 `import` 的区别是什么？没有它为什么做不到"加工具不改代码"？ |
| 3 | `workspace.py` | 围栏 + 禁区 | 为什么必须**先 `resolve()` 再判断**？`data/` 为什么只能读不能写？ |
| 4 | `read_file.py` / `list_dir.py` / `write_file.py` | 具体工具 | 每种失败的错误信息为什么写那么细？ |

**两个最容易忘的点**

*先展开再判断*：

```
"../../Windows/System32"          字符串里看不出问题
    ↓ resolve()
"C:/Windows/System32"             现在藏不住了
    ↓ is_relative_to(root)
False → 拒绝
```

顺序反了，`..` 没展开就去比对，什么都拦不住。

*`data/` 是禁区*：里面是聊天存档和长期记忆。**记账的会计不能自己改账本。**
模型答错一次是一次的事，它要是能改自己的记忆，错误会被写进下一次的开场白，反复喂给自己。
所以 `write_file` 走 `resolve_for_write()`，比 `resolve()` 多一道禁区检查；`read_file` 不走 —— 读是允许的。

*会改动东西的工具，动手前先问*（改造 5）：每个工具自己声明 `read_only`，默认 `False`（要问）；
五个只读工具（`read_file`、`list_dir`、`search_text`、`echo`、`load_skill`）声明了 `True`。
runner 执行 `read_only=False` 的工具之前，先调订单里的 `confirm(工具名, 参数)`：
`main.py` 传的是在终端里问你的 `ask_permission`，测试传 `None` 就不问。
新工具 `run_command` 在工作区里跑命令——它**绕得过围栏和禁区**，挡在它前面的只有这一问。

**验证**：`python main.py`，让它"用 write_file 把 data/memory/MEMORY.md 改成 xxx"，
应该被拒绝，而且拒绝信息里告诉它该怎么办。再试 `tests/test_protected_paths.py` 的负对照：
把 `write_file.py` 里的 `resolve_for_write` 改回 `resolve`，跑测试，看红两个。

### 第 4 步 · 模型层：`providers/` + `config/`

| 顺序 | 文件 | 一句话 | 带着什么问题 |
|---|---|---|---|
| 1 | `providers/base.py` | 契约：一次模型调用长什么样 | 为什么 runner 只能看到 `provider.chat()` 这一个方法？ |
| 2 | `providers/openai_compat.py` | 翻译官 | `raw` 为什么不能直接用 `model_dump()`？`arguments` 为什么要留两份？ |
| 3 | `providers/factory.py` | 查找表 | `main.py` 里为什么搜不到任何 Provider 类名？ |
| 4 | `config/schema.py` → `config/loader.py` | 配置的形状和入口 | 密钥为什么不写进 `config.json`？三块结构（providers / modelPresets / agents）各解耦了什么？ |

**三层各解耦一样东西**

```
config.json     解耦"参数值"    换 key、换 url、换模型名
factory.py      解耦"类的选择"  换厂商
base.py         解耦"调用方式"  主循环永远只调 provider.chat()
```

**验证**：把 `config.json` 的 `modelPreset` 从 `ds` 改成 `sf`（硅基流动），
不动任何代码跑一次 `python main.py`。能跑通，就证明这三层是真的解开了。

**一个已知的洞**：`chat()` 还没有重试和超时。402（余额不足）、429（限流）、
网络断开，现在都会直接把整个程序炸掉，用户那一轮输入就没了。
按分层约定它该关在 `openai_compat.py` 里 —— 对上层来说 `chat()` 要么成功、要么彻底失败。
记在待办里。

### 第 5 步 · 上下文层：五个文件，两道防线

这是项目里最厚的一层。按这个顺序读，每个文件的 docstring 都先读完再看代码：

| 顺序 | 文件 | 一句话 | 带着什么问题 |
|---|---|---|---|
| 1 | `agent/prompts.py` | 模板文件在哪，只有这一处知道 | 为什么单独开一个模块？（`prompts/` 下有 `compaction.md` 和 `dream.md`） |
| 2 | `agent/context.py` | 系统提示按变动频率分层拼装 | 为什么稳定的放前面？记忆为什么不能加进 `LAYERS`？ |
| 3 | `agent/tokens.py` | 尺子：估算多少 token | 为什么不装分词器？系数怎么来的？ |
| 4 | `agent/payload.py` | 存档 → 这次要发的（截断 + 清理） | 铁律是什么？两道工序各在什么时候做？ |
| 5 | `agent/compaction.py` | 超预算时压成摘要 | 为什么不能塞进 `build_payload`？摘要消息为什么用 `system` 角色？ |

**两道防线，按成本排队**

```
0 ─────── 100,000 ─────────── 190,000 ──────────► 1M（模型硬上限）
             │                     │
     CLEAR_TRIGGER          CONTEXT_BUDGET
     清理旧工具结果            摘要压缩
     不花钱，早点做             要多调一次模型，最后才做
     ← payload.py             ← compaction.py
```

摘要压缩的触发条件问的是"**免费手段用完之后还超不超**"：
`estimate_tokens(build_payload(messages)) <= budget`。量的是加工之后的大小，不是原始大小。

**系统提示的分层**（`context.py`）

```
SOUL.md        我是谁                  几乎不变     ← 缓存永远命中
AGENTS.md      在这个工作区怎么做事      跟项目走
运行时          工作区根目录            换目录才变
长期记忆        MEMORY.md 正文          每次整理后可能变  ← 放最后
```

模型缓存从第 0 个 token 开始逐个匹配，中间改一个字，后面全部失效。
所以**变得勤的往后放**。

**验证**

- `python -m scripts.check_tokens` —— 尺子和真实 usage 对一下账
- `payload.py` 里有两处"先复制再改"，各有一个测试守着，负对照要配对着做：
  - 工序一（截断）的 `shrunk = dict(msg)` 改成 `shrunk = msg`
    → 红的是 `tests/test_runner.py` 的 `test_archive_keeps_full_text_while_model_sees_truncated`
  - 工序二（清理）的 `replaced = dict(msg)` 改成 `replaced = msg`
    → 红的是 `tests/test_payload.py` 的 `test_archive_and_structure_untouched`

  `test_archive_and_structure_untouched` 用的工具结果只有 3,000 字符，够不着截断那条线，
  所以它守不住工序一（这里早先把两者配错了，实际做负对照时才发现）
- `tests/test_compaction.py` 的 `test_covered_is_correct_after_a_second_compaction`：
  读懂它为什么要压两次

### 第 6 步 · 存储层：三个文件，越往下越"笨"

| 顺序 | 文件 | 知道什么 | **不知道**什么 |
|---|---|---|---|
| 1 | `session/manager.py` | 会话有生命周期、带一条摘要记录 | jsonl 是什么、摘要消息什么格式 |
| 2 | `session/messages.py` | 怎么读写 jsonl、三种行怎么区分 | "会话"是什么概念 |
| 3 | `storage/jsonl.py` | 逐行读字典、跳过坏行 | 记录里有什么字段 |

**检验分层的办法**：想把存储从 jsonl 换成 SQLite，**只需要重写 `messages.py`**，
`manager.py` 一行不用改。想让流水账也用同样的读法，**只需要 import `storage/jsonl.py`**。

**jsonl 里的三种行，靠有没有 `role` 键区分**

```
{"role": ...}          消息        load_messages 认
{"_meta": {...}}       文件头      load_meta 认
{"_summary": {...}}    摘要便条    load_summary 认
```

以后想加新类型的记录，只要不叫 `role`，就不会污染消息列表。

**坏行怎么办**：追加写 + 断电，文件末尾会留半行。老写法一行坏掉整个会话读不出来；
现在跳过那一行、警告一次、其余照常。**丢半句 ≠ 丢全部。**

**坏行还不能连累下一条**（第 35 讲）：半行末尾没有换行符，下一次追加会直接焊在它后面，
两条粘成一行、一起被扔掉。所以所有追加都走 `storage/jsonl.py` 的 `append_record()`，
写之前先看最后一个字节，不是换行就先补一个。这个坑是情景模拟时真撞出来的。

**验证**：`tests/test_broken_lines.py` 的第一个测试。手动往一个会话文件末尾追加半行
`{"role": "user", "content": "断了`，然后 `python main.py --session 那个key`，
应该看到一条警告、其余消息正常恢复。

### 第 7 步 · 记忆层：`agent/memory.py`（阶段五，已完成）

**先看比喻，再看代码**：这一层是会计的记账方式。

```
① 聊天记录          ② 流水账                ③ 便利贴
（原始凭证）   →    （一条条事实）    →      （贴在额头上）
data/sessions/      history.jsonl            MEMORY.md
永远存全文           只追加，带编号            开机时拼进系统提示
    ↑                    ↑                        ↑
  已经有了          第 25/26 讲做了          第 24 讲做了读，
                                            第 27 讲做写（Dream）
```

**带着什么问题读**

- 便利贴（MEMORY.md）为什么放 `data/` 不放 `templates/`？（谁写 / 进不进 git / 缺了是不是错）
- 流水账的 `cursor` 是干什么的？和 `_summary.covered` 是同一个思路吗？
- 流水账的 `session` 字段为什么重要？
- 事实是**什么时候**被写进流水账的？为什么挂在压缩上？
- `append_fact` 的 `path` 参数默认值为什么是 `None` 而不是 `HISTORY_FILE`？

**四个标签 = 保质期**

| 标签 | 管多久 | 例子 |
|---|---|---|
| `permanent` | 一直 | 用户用 Windows、说中文 |
| `durable` | 几个月 | 项目用 Chroma、定下的架构 |
| `ephemeral` | 几周 | 当前在做阶段五 |
| `correction` | 推翻旧的 | "模型名是 X，不是 Y" |

**五个动作的分工**

| 动作 | 什么时候发生 | 干什么 |
|---|---|---|
| `append_fact` | 压缩时顺便（第 26 讲） | 记一笔流水，不判断对错 |
| `dream` | 敲 `/dream`、或退出时（第 27 讲） | 读流水账 → 整理 → **覆盖**总账 |
| `read_memory` | 启动时、`/dream` 之后 | 读总账，拼进开场白 |
| `correct_fact` | 敲 `/correct`（第 29 讲） | 记一笔 `[correction]` 流水，然后立刻整理一次 |
| `trace_fact` | 敲 `/why`（第 29 讲） | 在流水账里按关键词找出处，回答"这句话哪来的" |

**Dream 的四条铁规矩**（不变量 8）

- **没正常跑完，绝不推进游标**。推进了就等于宣布"这批整理进去了"，
  要是其实没有，这批事实永远不会再被看一眼。
- **模型返回空时不覆盖总账**。"没返回内容"不等于"记忆该清空"。
- **新记忆缩水太多时也不覆盖**（第 35 讲）。模型回一句"好的。"也算"有内容"，
  以前会拿这三个字换掉整本记忆。现在新记忆不到旧的 `MIN_KEEP_RATIO`（0.34）就拒绝。
- **游标推到这批里最大的编号**（第 35 讲），不是"最后一条"的编号。
  顺序乱过一次，拿最后一条就会把中间几条永久跳过去，而且一句提示都没有。

写盘本身也是原子的：先写临时文件再 `os.replace`，断电时磁盘上要么是旧版、要么是新版，
不会出现半篇记忆。

**整篇覆盖的两个风险，第 28 讲兜住了**

投毒实验（往流水账塞一条假事实再跑 Dream）撞出两件事：

    ① 错事实被并进去          意料之中
    ② 一条旧记忆被**悄悄漏抄**  意料之外，屏幕上只说"整理了 1 条事实"

所以加了两样，都不指望模型配合：

| | 干什么 |
|---|---|
| 快照 | 覆盖前先存一份带时间戳的副本 → 退得回去（`/memory-undo`） |
| diff | **程序**比对前后两版逐行报告 → 看得见实际改了什么（`/memory-log`） |

**diff 必须程序算，不能问模型。** 模型漏抄一条时它自己不知道 ——
问它"你改了什么"，它只会复述它**打算**做的事。nanobot 的注释写得很直白：
*"Pure filesystem/git ground truth — never LLM narrative"*。

**验证**

- `python -m scripts.check_facts` —— 看真模型能提炼出什么事实
- `python main.py` → `/dream` 看实际改动 → `/memory-log` 看历史 → `/memory-undo` 退回去
- `tests/test_dream.py` 重点读 `test_failed_dream_can_be_retried`（失败不是死局）
- `tests/test_snapshot.py` 重点读 `test_undo_is_itself_undoable`（撤销也要能撤销）

**记错了怎么办**（第 29 讲）：`/correct 正确的说法` 记一笔 `[correction]` 流水，
然后**立刻**整理一次 —— 敲这条命令的那一刻，你刚发现记忆是错的，
没有理由让它带着错再活一会儿。

纠正**不直接改总账**：流水账只能追加（不变量 7），错了就再记一笔冲正，
让下一次整理去合并。这是会计的做法，也方便回答"为什么改"。

配套的 `/why 关键词` 回答"这句话是哪来的"：流水账每条都带 `session`
（第 25 讲埋的伏笔），顺着它 `python main.py --session <key>` 就能翻回当初那次对话的原文。

**验证（第 29 讲）**

- `tests/test_correction.py` 10 个测试，重点读
  `test_correction_never_rewrites_the_journal`（纠正是追加，不是涂改）

  `test_cursor_advances_to_the_largest_in_the_batch`——后者一开始负对照不红，

  → `/why Chroma` 看这条事实的出处和所属会话

### 第 8 步 · 测试：怎么读，以及负对照

`tests/` 下每个文件对应一层。**每个测试的 docstring 末尾都写了"负对照"**：
把代码改成那样，这个测试必须红。

读测试的方法不是从头看到尾，而是：

1. 读测试名，猜它在守什么
2. 读 docstring 里的负对照，**真的去改坏**，跑，看它红
3. 改回来，跑，看它绿

一个测试如果改坏了代码还是绿的，那它是假的安全感。项目里有过这种教训。

**两个一次性脚本**（不属于 Agent，项目里没有代码 import 它们）

| 脚本 | 干什么 | 什么时候跑 |
|---|---|---|
| `scripts/check_tokens.py` | 尺子 vs 真实 usage 对账 | 换模型、改系数之后 |
| `scripts/check_facts.py` | 调小触发线，看真模型提炼出什么事实 | 改了压缩提示词之后 |

都要用 `python -m scripts.xxx` 运行，不能 `python scripts\xxx.py`（否则找不到 `agent` 包）。

## 第二部分 · 设计说明：为什么是这样

### §1 分层规则表：每层知道什么、不知道什么

这张表是整个项目的骨架。每次加新东西，先想清楚它属于哪一行。

| 层 | 文件 | 知道什么 | **不知道**什么 |
|---|---|---|---|
| 编排 | `main.py` | 命令行、怎么打印、一轮的先后顺序 | 会话存在哪、循环转几圈 |
| 执行 | `agent/runner.py` | 怎么转循环、工具怎么执行 | `SOUL.md` 存在、在调哪家模型 |
| 上下文 | `agent/payload.py` | 怎么加工"这次要发的" | 谁会发它、发给谁 |
| 上下文 | `agent/compaction.py` | 摘要消息长什么样、切在哪 | jsonl 长什么样 |
| 上下文 | `agent/context.py` | 各层怎么排、怎么拼 | 记忆和技能清单从哪来（都只收到一段文本） |
| 模型 | `providers/base.py` | "调一次模型"长什么样 | 任何具体厂商 |
| 模型 | `providers/openai_compat.py` | 怎么把 SDK 返回翻译成统一形状 | messages 怎么攒出来的 |
| 存储 | `session/manager.py` | 会话有生命周期、带一条摘要记录 | jsonl 是什么、摘要消息什么格式 |
| 存储 | `session/messages.py` | 怎么读写 jsonl | "会话"是什么概念 |
| 存储 | `storage/jsonl.py` | 逐行读字典、跳过坏行 | 记录里有什么字段 |
| 工具 | `agent/tools/workspace.py` | 路径在不在围栏内、在不在禁区 | 文件存不存在 |
| 记忆 | `agent/memory.py` | MEMORY.md 和流水账在哪、怎么读写 | 系统提示长什么样、什么事值得记 |
| 技能 | `agent/skills.py` | 技能目录在哪、frontmatter 怎么解析、正文怎么取 | 清单怎么拼、正文怎么发给模型、谁在调它 |
| 工具 | `agent/tools/load_skill.py` | 怎么把一个技能名变成一段正文 | 技能目录在哪、frontmatter 长什么样（都问 `skills.py`） |

**检验一个函数放对没放对的办法**：看它 import 了什么。
`runner.py` 里如果出现了 `from session import ...`，那就是放错了。

### §2 一条消息的旅程

以"读一下 runner.py"为例，跟着一条消息走完全程：

```
你敲的字
  │
  ├─ main.py           messages.append({"role":"user", ...})      ← 内存
  │
  ├─ runner.py 第1圈    build_payload(messages) → provider.chat()
  │                     模型说：我要调 read_file
  │                     messages.append(assistant, tool_calls=[...])
  │
  ├─ runner.py         tool.execute("agent/runner.py")
  │                     ↓ workspace.resolve() 先展开再判断
  │                     ↓ 读文件，返回全文 20,000 字
  │                     messages.append(tool, content=全文)        ← 存的是全文
  │
  ├─ runner.py 第2圈    build_payload(messages)
  │                     ↓ 那条 tool 消息在 payload 里被截到 8,000 字   ← 只改副本
  │                     → provider.chat()
  │                     模型说：它是主循环执行器。
  │                     messages.append(assistant, content="...")
  │                     没有 tool_calls → break
  │
  ├─ main.py           session.save_turn(messages[boundary:])
  │                     ↓ manager → messages.py → open("a") 追加
  │                     磁盘上 4 行：user / assistant / tool（全文）/ assistant
  │
  └─ main.py           print("AI > ...")
```

**同一条工具结果，三个地方三种形态**：

| | 内存 `messages` | 磁盘 jsonl | `payload` |
|---|---|---|---|
| 内容 | 全文 20,000 字 | 全文 20,000 字 | 截到 8,000 字 |
| 活多久 | 一次运行 | 永久 | 一圈 |
| 能不能改 | 能 | **只能追加** | 随便改 |

下一次启动、恢复这个会话，`restore_history()` 从磁盘读回全文，
然后每一圈 `build_payload` 再重新截一次。**截断阈值改了，历史立刻按新值生效。**

### §3 三份 messages 的区别（最容易绕晕的地方）

| 名字 | 在哪 | 谁生产 | 谁消费 | 里面有系统提示吗 | 里面有摘要消息吗 |
|---|---|---|---|---|---|
| 存档 | `data/sessions/*.jsonl` | `save_turn` | `resume` | ❌ 永不 | ❌ 只有 `_summary` 便条 |
| 内存 | `main.py` 里的 `messages` | `restore_history` + 每轮追加 | `runner` | ✅ 下标 0 | ✅ 压缩过就有，下标 1 |
| payload | `build_payload` 的返回值 | 每圈现造 | `provider.chat` | ✅ | ✅ |

**存档最干净**：只有真实发生过的对话（user / assistant / tool）。
系统提示每次启动重新拼，摘要每次启动重新造。
好处：改了 `SOUL.md`，所有历史会话下次加载都用新的；换了压缩策略，旧存档照样能用。

### §5 两道防线与阈值

| 常量 | 值 | 在哪 | 出处 |
|---|---|---|---|
| `MAX_TOOL_RESULT_CHARS` | 8,000 | `payload.py` | 单条上限，与总量无关。8,000 中文字符 ≈ 4,800 token，贴着 Agent Skills 规范建议的「SKILL.md 正文 5,000 token 以内」（第 32 讲从 4,000 调上来） |
| `CLEAR_TRIGGER` | 100,000 | `payload.py` | Anthropic context editing 的 `trigger` 默认值 |
| `CLEAR_AT_LEAST` | 20,000 | `payload.py` | Anthropic 的 `clear_at_least`，避免频繁打断提示缓存 |
| `KEEP_TOOL_RESULTS` | 3 | `payload.py` | Anthropic 的 `keep` 默认值 |
| `CONTEXT_BUDGET` | 190,000 | `payload.py` | nanobot 公式；只占 1M 窗口的 19%，余量是为了**质量**不是怕装不下 |
| `KEEP_RECENT_RATIO` | 0.5 | `compaction.py` | 压缩时至少保留半个预算的原文 |
| `NO_WRITE_DIRS` | `(项目目录 / "data",)` | `workspace.py` | 禁区。放的是完整路径，锚代码位置，不跟着工作区走 |
| `MAX_FACT_CHARS` | 500 | `memory.py` | 流水账单条上限，防模型把整段输入当摘要吐回来。第 35 讲从 `MAX_CONTENT_CHARS = 4,000` 改名并下调：和 `write_file.py` 的同名常量（100,000）撞名；且一条是一句话，4,000 的保险丝比失火范围还大。nanobot 的同类是 `_HISTORY_ENTRY_HARD_CAP = 64_000`，它一条是整段摘要 |
| `MIN_KEEP_RATIO` | 0.34 | `memory.py` | 新记忆短于旧的这个比例就不覆盖（第 35 讲）。拍的数：正常整理缩掉一小半很常见，缩到三分之一就可疑。误伤了事实还在流水账里，再 `/dream` 一次即可 |
| `DEFAULT_MAX_ITERATIONS` | 30 | `config/loader.py` | 一轮最多转几圈，`config.json` 的 `agents.defaults.maxIterations` 可改。实测改一行说明用了 8 圈，原来写死的 10 太紧 |

**单位约定**：这张表里凡是 `_CHARS` 结尾的，数的都是**字符**（Python 的 `len`，一个汉字算 1），不是字节。

**两个成本模型上的结论，都查过出处**（凭推理下过错结论，吃过亏）：

- "一次多清一点"是有收益的：`CLEAR_AT_LEAST` 就是为此存在的 —— 每清一次都会打断提示缓存，
  清得太勤反而更贵。
- `CONTEXT_BUDGET` 定在 19% 不是怕装不下，是模型在长上下文里质量会下降。

**一个还没解决的矛盾**：190,000 这条线是照 1M 窗口定的，但事实提炼挂在它上面，
导致记忆几乎不会被写（见第一部分第 7 步）。第 27 讲处理。

### §6 「为什么放在这里」

每条都是一个曾经可以放在别处、最后选了现在这个位置的决定。

| # | 什么 | 放在哪 | 而不是 | 为什么 |
|---|---|---|---|---|
| 1 | 截断工具结果 | `payload.py`，发送前 | 工具执行时 | 存档要保真；阈值改了历史立刻生效 |

| 4 | 摘要 | `_summary` 便条 + 现场重造 | 替换存档原文 | 压缩有损，原文一直在才能换策略 |
| 5 | 长期记忆 MEMORY.md | `data/memory/` | `templates/` | Agent 写的 / 不进 git / 缺了是常态不是错 |
| 6 | 读 MEMORY.md | `main.py` 读好传给 `context.py` | `context.py` 自己读 | 让 `build_system_prompt` 保持纯函数，不碰磁盘 |

| 9 | 提示词正文 | `templates/*.md` | `.py` 里的字符串 | 一天改五遍的东西不该混进代码提交 |
| 10 | 模板目录路径 | `prompts.py` 一处 | `context.py` 和 `compaction.py` 各写 | 挪目录只改一处 |
| 11 | Provider 类的选择 | `factory.py` 查表 | `main.py` 写类名 | 换厂商只改配置 |
| 12 | 网络重试超时 | 该在 `openai_compat.py`（**待办**） | `runner.py` | 对上层，`chat()` 要么成功要么彻底失败 |
| 13 | 摘要消息的格式 | `compaction.py` | `manager.py` | 想改角色只动一处，存储层不知道 |
| 14 | 提炼事实 | 挂在压缩那次调用上 | 单独再调一次 | 模型已经读完历史了，顺便多写一节；分两次多花一次钱 |
| 15 | 逐行读 jsonl | `storage/jsonl.py` | `messages.py` 内部 | 流水账也要用 —— **撞到第二次才抽出来** |
| 16 | 流水账 `path` 默认值 | `None`，函数里才取 | `= HISTORY_FILE` | 后者在 def 那一刻就定死，测试换不掉，会污染真实记忆 |
| 17 | Dream 写 MEMORY.md | `memory.py` 里直接 `write_text` | 走 `write_file` 工具 | 围栏拦的是模型，不是我们自己；这样禁区不用开口子 |
| 18 | Dream 的触发 | 退出时 + 手动 `/dream` | 只靠超预算压缩 | 压缩线 190k 几乎够不着，记忆等于永远不写 |
| 19 | 系统提示 | 改成函数，变了才重算 | 模块级算一次 / 每轮重算 | `/dream` 会中途改记忆；但每轮重算白丢提示缓存 |
| 20 | 算 diff | 程序用 `difflib` 比对 | 让模型汇报改了什么 | 模型漏抄时自己不知道；它只会复述**打算**做的事 |
| 21 | 快照时间戳 | 精确到微秒 + 撞名保护 | 精确到秒 | "整理完马上回滚"会落在同一秒，后者覆盖前者 |
| 22 | 拍快照的位置 | `dream()` 里、覆盖之前 | 函数开头 | 前面任何一步失败都没改文件，存它干什么 |
| 23 | `/` 开头的命令 | 主循环里拦掉 | 发给模型 | 它们是给程序看的；发过去白花一轮钱 |
| 24 | 纠正记错的事实 | 追加一条 `[correction]` 再整理 | 直接改 `MEMORY.md` | 流水账只能追加（不变量 7）；直接改总账没人知道为什么改 |
| 25 | `/correct` 之后的整理 | 立刻跑一次 `dream` | 等下次 `/dream` | 你刚发现记忆是错的；而且很容易转头就忘了还挂着一条纠正 |
| 26 | 技能叫什么名字 | 取**目录名**，frontmatter 的 `name` 只用来校验 | 取 frontmatter 的 `name` | 目录名就是路径的一部分，模型要靠它拼路径读正文；两者分家就得多维护一张映射表。Agent Skills 规范本来也要求两者一致 |
| 27 | 技能写坏了 | 跳过 + `warnings.warn` | 启动时报错 / 静默跳过 | 技能是**可选扩展**，坏一个不该让 Agent 起不来（对比 `templates/` 缺文件直接炸）；但悄悄跳过会让你以为装好了 |
| 28 | 技能目录在哪 | 锚 `__file__`（`SKILLS_DIR`），函数仍收 `root` 参数 | 锚 cwd | 技能是人写的、跟着代码走（和 `templates/` 同款）；换个目录启动技能还在。代价：技能落在工作区外，`read_file` 读不到 |
| 29 | 模型怎么读技能正文 | 专用工具 `load_skill(name)` | `read_file` 读路径 / 给围栏开只读口子 | 开口子要动三个文件共用的 `workspace.py`，还得连写测试守住新开的口；新增工具只多一个文件（自动发现）。顺带：模型永远不碰路径 |
| 30 | 技能名的安全检查 | **查表**（只认清单里有的名字） | `workspace.resolve` 那套先展开再判断 | 合法范围有限时白名单更省也更稳：`../..` 永远不会出现在清单里。范围无限（`read_file`）才需要边界检查 |
| 31 | 技能正文超过单条上限 | 阈值提到 8,000，工具只 warn 不截断 | 给技能正文开豁免 | 豁免要让 `payload.py` 知道"这条工具结果是技能返回的"，上下文层就被迫知道技能存在；warn 走 stderr，不进上下文 |
| 32 | 技能清单在系统提示的位置 | 运行时之后、**记忆之前** | 记忆之后（nanobot 的顺序） | 排序按"内容变得勤不勤"：记忆每次 Dream 都可能变，清单只在装/删技能时变。排反了的话，每跑一次 Dream，后面整段清单的缓存都白丢 |
| 33 | 一个技能都没有时 | 整段不出现，连标题都不留 | 留一个空的「# 技能」段 | 空清单会让模型以为"有这套机制但一个都没装"，可能去猜名字白调一轮。和记忆同款 |

| 36 | 防模型答歪 | 按**比例**的缩水闸门 `MIN_KEEP_RATIO` | 固定最少字数 / 不防 | 记忆越长越长，固定字数很快失效；比例跟着一起长 |
| 37 | 写 MEMORY.md 和游标 | 临时文件 + `os.replace` | 直接 `write_text` | `write_text` 先清空再写，断电留下半篇；快照救不了这一版（快照拍的是上一版） |
| 38 | 模型自创的标签 | 留着，落盘时降级成 `durable` | 解析时直接丢 | 为一个标签名丢掉一条真事实不划算；以前两个函数一个说丢、一个说降级，实际是丢 |
| 39 | 配置文件在哪找 | 锚 `__file__`（`CONFIG_FILE`），函数仍收 `path` 参数 | 相对启动目录的 `"config.json"` | 配置跟着程序走；在别的项目里启动（工作区 = 那个项目）也找得到。默认值写 `None` 到函数里才取，测试才换得掉（同第 16 条） |
| 40 | 禁区按什么算 | 一个固定的完整路径：Agent 自己的 `data/` | 工作区下叫 `data` 的目录 | 要保护的是存档和记忆，不是"名字叫 data 的目录"。旧写法在别的项目里白挡人家的 `data/`，在上级目录启动时真存档反而没人管 |
| 41 | MCP server 的脚本路径 | `load_mcp_servers` 里按配置文件所在目录解析（`_anchor`），只换真有其文件的那几项 | 原样交给子进程 / 把子进程的工作目录改成项目目录 | 原样交出去，相对的是启动目录；改子进程工作目录又会让以后的文件类 server 看错地方。只把脚本位置钉死，server 仍跟着工作区走 |
| 42 | MCP server 的日志 | 锚 `__file__`（`LOG_DIR`） | 相对启动目录的 `data/mcp_logs` | 日志是 Agent 自己的东西，不该撒到你干活的项目里 |
| 43 | 文件太长怎么办 | `read_file` 自己分段（`_page`）：整行整行地给，末尾告诉模型接着读的 `offset` | 返回全文，交给发送前的截断 | 截断只留开头，模型看不到后面、也不知道怎么继续——连本项目的 `main.py` 都读不全。代价：大文件在存档里是一段一段的，不再是全文（第 1 条对它不再成立）；发送前的截断留着给别的工具兜底 |
| 44 | `old_text` 对上不止一处 | 一处都不改，报出现了几次 | 改第一处 | 程序不知道模型想改哪处；猜错了文件被悄悄改坏，回执还写着"已修改" |
| 45 | 搜索怎么匹配 | 按原样匹配（`search_text`） | 正则表达式 | 模型很容易写出不合法的正则；原样匹配不会出错。工具名也不叫 `grep`，免得模型按正则的习惯去用 |
| 46 | 搜索结果太多 | 工具自己截：最多 50 处、每处 200 字符，末尾说明一共多少 | 交给发送前的截断 | 条目级截断给的是完整的若干行；字符级截断可能把一行切成半截（同 `list_dir` 的 `MAX_ENTRIES`） |
| 47 | 改文件时的换行 | 比对前统一成 `\n`，写回前还原成文件原来的换行 | 直接按文本读写 | 模型看到的原文是 `\n` 的；不还原的话改一行，git 认为整个文件都变了 |
| 48 | 圈数上限的默认值放哪 | 配置层（`DEFAULT_MAX_ITERATIONS = 30`），`main.py` 读出来填进订单 | 直接改 `AgentRunSpec` 的默认值 | 30 是这个程序的选择，不是循环本身的属性；runner 不该知道配置文件存在。订单的默认值 10 留着，不牵动现有测试 |
| 49 | 按 Ctrl+C 怎么收场 | 入口处 `except* (KeyboardInterrupt, CancelledError, EOFError)`，说一声就退出 | 普通的 `except KeyboardInterrupt` / 不管 | 连着 MCP server 时中断被包进好几层异常组，普通 `except` 看不见；而且 Windows 控制台里停在 `input()` 上按 Ctrl+C，实际抛出的是 `EOFError`——这是照着真实报错改的，一开始按"应该是 KeyboardInterrupt"写就没生效 |
| 50 | 动手前问谁 | runner 调订单里传进来的 `confirm(工具名, 参数)`；`main.py` 传 `ask_permission` | runner 里直接 `input()` | 循环层不碰产品层：runner 不知道是终端、网页还是自动评估在回答。测试和以后的评估任务集传 `None` 就不问；以后接界面只换这一个函数 |
| 51 | 哪些工具要问 | 工具自己声明 `read_only`，基类默认 `False`（要问） | 默认 `True` / 在 runner 里维护一张"要问的工具"名单 | 忘了声明时，默认要问只是烦，默认不问是危险；有没有副作用是工具自己最清楚的事。MCP 工具也走默认值：别人写的工具先当它会改东西 |
| 52 | 用户拒绝了怎么回 | 一条普通的 tool 消息 `DENIED_TEXT` | `ToolResult.error` / 不回 | 工具没坏，套上 `TOOL_ERROR_HINT` 的"检查参数是否正确"会把模型往错的方向引；不回的话违反第 3 条不变量，下一次请求直接被接口拒掉 |
| 53 | 输入什么算同意 | 只有 `y` / `yes`；回车、乱敲、Ctrl+C（Windows 上是 `EOFError`）都算拒绝 | 回车算同意 | 手滑的代价应该是"没执行"，不是"误执行" |
| 54 | 命令在哪个 shell 里跑 | 系统默认（Windows 是 `cmd.exe`），`create_subprocess_shell` 一行搞定 | PowerShell（nanobot 的选择） | 一行代码跨平台；Windows 自带的 PowerShell 5.1 不支持 `&&`，而模型最习惯写 `cd x && y`。看文件、搜文字本来就有专门的工具 |
| 55 | 命令输出怎么解码 | **逐行**：先 UTF-8，不行按系统编码（中文 Windows 是 GBK） | 整段一起解 | 实测 `git log && echo 中文`：git 吐 UTF-8，cmd 的 echo 吐 GBK，整段解时 git 那几行全成了乱码 |
| 56 | 命令输出太长 | 工具自己剪：留开头 2,000 + 结尾，总长在发送前的单条上限之内 | 交给发送前的截断 | 发送前的截断只留开头；命令最要紧的常常在结尾（测试汇总、最后那行报错） |
| 57 | 退出码不是 0 | 照常返回"退出码：N + 输出"，不标成错误 | 标成错误 | 测试没过也是命令正常跑完了；标成错误会追加"不要用同样的参数重试"，可改完代码恰恰要原样再跑一遍 |

| 59 | 合并后的输出顺序 | 子进程环境变量加 `PYTHONUNBUFFERED=1` | 不管 / 把标准输出和标准错误分开交给模型 | 实测 Python 子进程"先 print、后报错"，模型收到的却是报错在前：接在管子上时标准输出会先攒着，标准错误写一句送一句。分开交又丢了两者的相对顺序。只管得到 Python 子进程 |
| 60 | 循环里发生的事交给谁 | 订单里的 `on_event` 函数，runner 只交不存 | runner 自己写文件 / 钩子类（nanobot 的 `AgentHook`） | 循环层不碰产品层，和 `confirm` 同一招。测试用 `got.append` 收进列表，评估任务集也能自己收。钩子类等到需要"改变"循环行为、而不只是记下来时再说 |
| 61 | 事件长什么样 | 一个字典，`type` 区分 `turn` / `model` / `tool` | 每种事件一个类 | 写进 jsonl 就是一行；加字段不用改任何类型定义 |
| 62 | 事件存在哪 | `data/events/{key}.jsonl`，一个会话一个文件 | 存档里 / `data/sessions/` 下 | 存档用来恢复对话，混进去 `load_messages` 要多一道过滤；`list_keys` 会把 `sessions/` 下每个 `.jsonl` 都当成一个会话 |
| 63 | 一轮失败时 | 事件照留，不跟着回滚 | 跟着存档一起回滚 | 存档回滚是为了让对话自洽；那一轮的 token 是真花了，成本数据要照实 |
| 64 | 写事件失败 | 提醒一次，之后安静跳过 | 抛异常 | 事件是观察数据，不该让一轮对话失败（同 `Usage` 取不到时返回 0） |
| 65 | 轮数怎么数 | `EventLog` 打开文件时先读出已记到第几轮，接着往下数 | 每次启动从 0 数 | `--session` 恢复后轮数不重号 |

### §7 与 nanobot 的差异

不是功能等价实现，是为了理解其设计而做的重写。以下每条都核对过 nanobot 源码：

| 点 | nanobot | 本项目 | 理由 |
|---|---|---|---|
| 截断时机 | 执行工具时 | 发送前 `build_payload()` | 存档保真 |
| 压缩后保留多少原文 | 只保留还没发给模型的增量 | 最近半个预算的原文 | 摘要有损，最近的内容模型正在用 |
| token 估算 | `tiktoken` | 字符数 × 系数 | 拿 OpenAI 分词器数 DeepSeek 本来就是估算 |
| 会话文件头 | 无 | 首行 `_meta` | `--list` 只读一行 |
| 记忆写保护 | 提示词叮嘱 | 代码禁区 | 提示词是建议，代码是保证 |
| 摘要格式 | 整份都是 `- [标签] 事实` | 五项散文 + 末尾事实清单 | 我们的摘要还要负责"下一步""失败过的尝试" |
| 记忆触发 | 闲置 15 分钟 + 超预算 | 退出时 + 手动 `/dream` + 超预算 | 命令行没有常驻进程数闲置时间，"敲了 exit"是最接近的时刻 |
| Dream 怎么改记忆 | 受限 Agent，用 `edit_file` 精确改 | 一次调用，输出整篇覆盖 | 我们总账小，整篇重写风险可控；**先写死再抽象** |
| 记忆的版本管理 | git（dulwich），`/dream-log` `/dream-restore` | 带时间戳的快照文件，留最近 10 份 | 不想为此多一个依赖；`difflib` 标准库就够 |
| 流水账编号 | 单独的 `.cursor` 计数器文件 | 每次扫全文取最大值 | 单进程，几百行扫一遍不值一提；先写死 |
| 追加写 | `_append_history_record` 直接 `open("a")` | `append_record()` 先补齐上一行再写 | 读的时候两边都能跳过坏行，但只有补齐才挡得住坏行把下一条也拖下水 |
| 写 MEMORY.md | `write_memory` 直接 `write_text`（有 git 兜底）；原子写工具 `_write_text_atomic` 只用在重写 history 上 | 原子写 | 我们没有 git，写坏了没处取回，所以把它的原子写工具用到记忆本身上 |
| 技能清单的顺序 | 不排序，直接用 `iterdir()` 给的顺序 | 按名字排序 | 发给模型的前缀顺序稳定才命中提示缓存，和工具自动发现同一个理由 |
| 写坏的技能 | 照样列进清单，描述退化成目录名 | 跳过 + 警告 | 没有描述的技能模型根本不会用它，列出来只占 token；但要出声，否则你以为它装上了 |
| 技能名的校验 | 只对插件技能要求 `name` == 目录名，工作区和内置技能不校验 | 所有技能都校验 | 我们只有一种来源，不必分两套规矩 |
| 技能清单的位置 | 排在记忆**之后**；系统提示里还嵌着 `last_active` 时间戳等每轮可变内容 | 排在记忆**之前** | 它的前缀本来就不稳定，排序影响不大；我们的系统提示每一段都只在真被改动时才变，"变得勤的排最后"是实打实的收益 |
| 读技能正文 | `read_file` + 两处补丁（只读白名单 + 把 `skills/x` 映射到内置目录） | 专用工具 `load_skill(name)` | 不给围栏开口子；模型不碰路径，错名字时还能反向指路列出可用技能 |
| 命令在哪个 shell | Windows 上默认 PowerShell，可以传 `shell='cmd'` | 系统默认 shell（Windows 是 `cmd.exe`），不让模型选 | 见 §6 第 54 条 |
| 危险命令 | `deny_patterns` 正则黑名单（`rm -rf`、`format`……，还专门挡了往 `history.jsonl` / `.dream_cursor` 写的命令） | 没有黑名单，执行前逐条问用户 | 黑名单总有漏网的写法；确认让人看到完整的命令。代价是全靠人看，见 §9 |
| 命令输出上限 | 10,000 字符 | 7,800 字符：开头 2,000 + 结尾 | 要装进我们发送前的单条上限 8,000，免得它再截一刀、只留开头 |
| 循环里发生的事怎么通知外面 | 钩子类 `AgentHook`（`agent/hook.py`），十几个方法：`before_iteration`、`after_execute_tool`…… | 订单里一个 `on_event` 函数，收一个字典 | 我们只需要"记下来"，不需要在某一步改变循环；先写死再抽象 |
| 纠正与溯源 | 流水账记的是**整段摘要**（`append_history(summary, session_key=...)`，同样带出处）；查出处靠模型自己 `grep` | 流水账记的是**一条条事实**（带 `session`）；`/correct` 纠正、`/why` 程序化查出处 | 粒度更细、查询是确定性的；代价是每条事实都要单独写一行 |

**一处一致、但容易想当然的地方**：压缩**不改写存档**。nanobot 的
`Session.commit_summary_checkpoint`（`session/manager.py`）注释写明
*"Replace replay before a hidden boundary while preserving the transcript"* ——
它同样保留完整记录，只移动 `last_archived` 指针。

### §8 负对照：测试怎么写才不是假的安全感

**教训**：有过测试全绿、把代码改回旧行为**照样全绿**的情况。那种测试守不住任何东西。

所以现在的规矩：

1. 写完测试，**先把代码改坏一遍**，确认测试真的会红
2. 改回来，确认绿
3. 把"改成什么样会红"写进测试的 docstring 末尾

例：

```python
def test_write_file_cannot_touch_memory(sandbox):
    """★ 不变量 6：主 Agent 不能改长期记忆。

    负对照：write_file 里把 resolve_for_write 改回 resolve → 变成成功回执。
    """
```

**做负对照时必须清 `__pycache__`**（第 28 讲踩到的）：

Python 判断字节码缓存还能不能用，看的是源文件的**修改时间（秒）+ 字节数**。
负对照经常是等长替换（`+= 1` ↔ `-= 1`、`>` ↔ `>=`），改坏和还原又发生在同一秒内 ——
两个条件都没变，Python 就直接用旧缓存，**你以为在测新代码，其实跑的是上一版**。

第 28 讲就被这个骗过一次：源码里明明写着 `+= 1`，跑出来却是减一的行为。
所以负对照的标准动作是：

    改坏 → 清 __pycache__ → 跑 → 还原 → 清 __pycache__

一句话：`find . -name __pycache__ -type d -exec rm -rf {} +`（PowerShell：
`Get-ChildItem -Recurse -Directory __pycache__ | Remove-Item -Recurse -Force`）

**doctest 的边界**：例子写成 `>>>` 格式可以被 `--doctest-modules` 验证。
但**碰文件系统的例子不要写成 doctest** —— doctest 的 `globals()` 是模块全局的拷贝，
隔离不了。那种放 `tests/` 里用 `tmp_path`。

**假 Provider**：凡是要调模型的路径，测试里用 `StubProvider` / `FakeProvider`
返回事先准备好的内容。慢、花钱、结果不稳定的东西不进 pytest；
那部分用 `scripts/` 下的一次性脚本手动验收。

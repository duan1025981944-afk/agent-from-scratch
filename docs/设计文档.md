# mini_nanobot 设计文档 · 兼回顾路线图

> 这份文档回答两个问题：**从哪里开始把项目读一遍**（第一部分），
> 以及**为什么每样东西放在它现在的位置**（第二部分）。
>
> 隔一段时间没看、忘了怎么回事 —— 从第一部分按顺序读，一步一验证，
> 大约两三个小时能把整个项目重新装回脑子里。
> 想查某个具体设计的理由 —— 直接翻第二部分对应的小节。
>
> 每个源文件顶部的 docstring 都是那个文件自己的详细说明书（"这个文件是什么 /
> 不是什么 / 怎么用 / 例子"）。本文档不重复它们，只讲**文件之间的关系**和
> **跨文件的规矩**。读到某个文件时，先读它的 docstring，再回来看这里。

## 第一部分 · 回顾路线：一层一层往下读

### 全景图：七层，从外往里

```
                         你敲的字
                            │
   ┌────────────────────────┼────────────────────────────┐
   │ ① 编排层   main.py     │  先做什么、后做什么、怎么打印   │
   └────────────────────────┼────────────────────────────┘
                            │
   ┌────────────────────────┼────────────────────────────┐
   │ ② 执行层   agent/runner.py                           │
   │            调模型 → 要不要用工具 → 执行 → 再调        │
   └──────┬─────────────────┼──────────────────┬─────────┘
          │                 │                  │
   ┌──────┴──────┐   ┌──────┴──────┐   ┌───────┴────────┐
   │ ③ 工具层    │   │ ④ 模型层    │   │ ⑤ 上下文层      │
   │ agent/tools/│   │ providers/  │   │ context/prompts │
   │             │   │ config/     │   │ tokens/payload  │
   │             │   │             │   │ compaction      │
   └─────────────┘   └─────────────┘   └───────┬────────┘
                                               │
   ┌───────────────────────────────────────────┼─────────┐
   │ ⑥ 存储层   session/manager.py → session/messages.py │
   │            → storage/jsonl.py                       │
   └───────────────────────────────────────────┼─────────┘
                                               │
   ┌───────────────────────────────────────────┼─────────┐
   │ ⑦ 记忆层   agent/memory.py                          │
   │            data/memory/MEMORY.md（便利贴）           │
   │            data/memory/history.jsonl（流水账）       │
   └─────────────────────────────────────────────────────┘
```

**读的顺序就是这个编号。** 从外往里：先知道一轮对话的骨架，再看每根骨头。

每一步都有三样东西：**读什么、带着什么问题读、读完怎么验证**。
验证不是可选项 —— 读完没验证，等于没读。

### 第 1 步 · 编排层：`main.py`

**读什么**：先读文件顶部 docstring，再直接跳到 `main()` 函数最后那个 `while` 循环。

**带着什么问题读**

- 一轮对话分几步？每步的先后顺序为什么不能换？
- `boundary` 这个变量是干什么的？为什么必须在压缩**之后**记？
- 系统提示为什么是模块级算一次，而不是每轮算？

**答案的形状**（读完对一下）

```
① compact_if_needed()        超预算才压缩，一轮最多一次（要花钱）
② boundary = len(messages)   ★ 必须在 ① 之后：压缩会让列表变短
③ messages.append(user)
④ runner.run()               转循环
⑤ session.save_turn(messages[boundary:])   只落盘这轮新长出来的
⑥ print                      先落盘再打印
```

`boundary` 记错位置的后果：`save_turn` 会从错误的位置切，把旧消息重复写进存档。

**验证**：把 ② 挪到 ① 前面，跑一次真对话，看 `data/sessions/*.jsonl` 里有没有重复行。改回来。

**这一层的规矩**：它只懂顺序。它**不知道**会话存在哪、循环转几圈、系统提示写了什么。

### 第 2 步 · 执行层：`agent/runner.py`

**读什么**：docstring 全文（它把循环的形状画出来了），然后读 `AgentRunner.run()`。

**带着什么问题读**

- 循环里**唯一的分岔点**在哪？
- 为什么 `assistant` 和 `tool` 两条消息都要 append，不能只塞工具结果？
- 工具执行有三种情况（A 工具不存在 / B 参数是坏 JSON / C 正常执行），
  前两种为什么不抛异常、而是转成文字塞回给模型？
- `except asyncio.CancelledError: raise` 为什么必须写在 `except Exception` **前面**？

**答案的形状**

```
for i in range(max_iterations):
    payload = build_payload(messages)     # 加工成这次要发的
    reply = await provider.chat(payload)  # 调模型
    messages.append(reply.raw)            # 模型说的话先入链
    if not reply.wants_tools:             # ★ 唯一的分岔点
        break
    执行每个工具，把结果 append 进 messages
```

模型每次要么"要用工具"（继续转），要么"说完了"（退出）。**没有第三种可能。**

工具报错对模型来说和工具成功是同一件事 —— **都是一段文本**。它读完这段文本自己决定下一步。
抛异常会中断整个循环，Agent 就只剩"成功或崩溃"两条路；转成文本回给它，它能自己换个路径重试。
**这是 Agent 能自愈的根本。**

**验证**：`tests/test_runner.py` 有 6 个测试。读 `test_every_tool_call_is_answered_by_a_tool_role_message`，
然后把 runner 里"情况 A"那段的 `role: "tool"` 改成 `"assistant"`，跑测试，看它红。改回来。

**这一层的规矩**："循环层不碰产品层"。它**不知道** SOUL.md 存在、不知道在调哪家模型、不写盘。
换渠道、换模型、换存储，这个文件一个字都不用改。

### 第 3 步 · 工具层：`agent/tools/`

四个文件，按这个顺序读：

| 顺序 | 文件 | 一句话 | 带着什么问题 |
|---|---|---|---|
| 1 | `base.py` | 一个工具 = 一份说明书 + 一段代码 | `description` 为什么要写"不要用于……"这种反例？ |
| 2 | `loader.py` | 自动登记处 | `importlib.import_module` 和普通 `import` 的区别是什么？没有它为什么做不到"加工具不改代码"？ |
| 3 | `workspace.py` | 围栏 + 禁区 | 为什么必须**先 `resolve()` 再判断**？`data/` 为什么只能读不能写？ |
| 4 | `read_file.py` / `list_dir.py` / `write_file.py` | 具体工具 | 每种失败的错误信息为什么写那么细？ |

**两个最容易忘的点**

*先展开再判断*：

```
"../../Windows/System32"          字符串里看不出问题
    ↓ resolve()
"C:/Windows/System32"             现在藏不住了
    ↓ is_relative_to(root)
False → 拒绝
```

顺序反了，`..` 没展开就去比对，什么都拦不住。

*`data/` 是禁区*：里面是聊天存档和长期记忆。**记账的会计不能自己改账本。**
模型答错一次是一次的事，它要是能改自己的记忆，错误会被写进下一次的开场白，反复喂给自己。
所以 `write_file` 走 `resolve_for_write()`，比 `resolve()` 多一道禁区检查；`read_file` 不走 —— 读是允许的。

**验证**：`python main.py`，让它"用 write_file 把 data/memory/MEMORY.md 改成 xxx"，
应该被拒绝，而且拒绝信息里告诉它该怎么办。再试 `tests/test_protected_paths.py` 的负对照：
把 `write_file.py` 里的 `resolve_for_write` 改回 `resolve`，跑测试，看红两个。

### 第 4 步 · 模型层：`providers/` + `config/`

| 顺序 | 文件 | 一句话 | 带着什么问题 |
|---|---|---|---|
| 1 | `providers/base.py` | 契约：一次模型调用长什么样 | 为什么 runner 只能看到 `provider.chat()` 这一个方法？ |
| 2 | `providers/openai_compat.py` | 翻译官 | `raw` 为什么不能直接用 `model_dump()`？`arguments` 为什么要留两份？ |
| 3 | `providers/factory.py` | 查找表 | `main.py` 里为什么搜不到任何 Provider 类名？ |
| 4 | `config/schema.py` → `config/loader.py` | 配置的形状和入口 | 密钥为什么不写进 `config.json`？三块结构（providers / modelPresets / agents）各解耦了什么？ |

**三层各解耦一样东西**

```
config.json     解耦"参数值"    换 key、换 url、换模型名
factory.py      解耦"类的选择"  换厂商
base.py         解耦"调用方式"  主循环永远只调 provider.chat()
```

**验证**：把 `config.json` 的 `modelPreset` 从 `ds` 改成 `sf`（硅基流动），
不动任何代码跑一次 `python main.py`。能跑通，就证明这三层是真的解开了。

**一个已知的洞**：`chat()` 还没有重试和超时。402（余额不足）、429（限流）、
网络断开，现在都会直接把整个程序炸掉，用户那一轮输入就没了。
按分层约定它该关在 `openai_compat.py` 里 —— 对上层来说 `chat()` 要么成功、要么彻底失败。
记在待办里。

### 第 5 步 · 上下文层：五个文件，两道防线

这是项目里最厚的一层。按这个顺序读，每个文件的 docstring 都先读完再看代码：

| 顺序 | 文件 | 一句话 | 带着什么问题 |
|---|---|---|---|
| 1 | `agent/prompts.py` | 模板文件在哪，只有这一处知道 | 为什么单独开一个模块？ |
| 2 | `agent/context.py` | 系统提示按变动频率分层拼装 | 为什么稳定的放前面？记忆为什么不能加进 `LAYERS`？ |
| 3 | `agent/tokens.py` | 尺子：估算多少 token | 为什么不装分词器？系数怎么来的？ |
| 4 | `agent/payload.py` | 存档 → 这次要发的（截断 + 清理） | 铁律是什么？两道工序各在什么时候做？ |
| 5 | `agent/compaction.py` | 超预算时压成摘要 | 为什么不能塞进 `build_payload`？摘要消息为什么用 `system` 角色？ |

**两道防线，按成本排队**

```
0 ─────── 100,000 ─────────── 190,000 ──────────► 1M（模型硬上限）
             │                     │
     CLEAR_TRIGGER          CONTEXT_BUDGET
     清理旧工具结果            摘要压缩
     不花钱，早点做             要多调一次模型，最后才做
     ← payload.py             ← compaction.py
```

摘要压缩的触发条件问的是"**免费手段用完之后还超不超**"：
`estimate_tokens(build_payload(messages)) <= budget`。量的是加工之后的大小，不是原始大小。

**系统提示的分层**（`context.py`）

```
SOUL.md        我是谁                  几乎不变     ← 缓存永远命中
AGENTS.md      在这个工作区怎么做事      跟项目走
运行时          工作区根目录            换目录才变
长期记忆        MEMORY.md 正文          每次整理后可能变  ← 放最后
```

模型缓存从第 0 个 token 开始逐个匹配，中间改一个字，后面全部失效。
所以**变得勤的往后放**。

**验证**

- `python -m scripts.check_tokens` —— 尺子和真实 usage 对一下账
- `tests/test_payload.py` 的 `test_archive_and_structure_untouched`：
  把 `payload.py` 里 `shrunk = dict(msg)` 改成 `shrunk = msg`（直接改原件），跑测试，看红
- `tests/test_compaction.py` 的 `test_covered_is_correct_after_a_second_compaction`：
  读懂它为什么要压两次

### 第 6 步 · 存储层：三个文件，越往下越"笨"

| 顺序 | 文件 | 知道什么 | **不知道**什么 |
|---|---|---|---|
| 1 | `session/manager.py` | 会话有生命周期、带一条摘要记录 | jsonl 是什么、摘要消息什么格式 |
| 2 | `session/messages.py` | 怎么读写 jsonl、三种行怎么区分 | "会话"是什么概念 |
| 3 | `storage/jsonl.py` | 逐行读字典、跳过坏行 | 记录里有什么字段 |

**检验分层的办法**：想把存储从 jsonl 换成 SQLite，**只需要重写 `messages.py`**，
`manager.py` 一行不用改。想让流水账也用同样的读法，**只需要 import `storage/jsonl.py`**。

**jsonl 里的三种行，靠有没有 `role` 键区分**

```
{"role": ...}          消息        load_messages 认
{"_meta": {...}}       文件头      load_meta 认
{"_summary": {...}}    摘要便条    load_summary 认
```

以后想加新类型的记录，只要不叫 `role`，就不会污染消息列表。

**坏行怎么办**：追加写 + 断电，文件末尾会留半行。老写法一行坏掉整个会话读不出来；
现在跳过那一行、警告一次、其余照常。**丢半句 ≠ 丢全部。**

**验证**：`tests/test_broken_lines.py` 的第一个测试。手动往一个会话文件末尾追加半行
`{"role": "user", "content": "断了`，然后 `python main.py --session 那个key`，
应该看到一条警告、其余消息正常恢复。

### 第 7 步 · 记忆层：`agent/memory.py`（阶段五，进行中）

**先看比喻，再看代码**：这一层是会计的记账方式。

```
① 聊天记录          ② 流水账                ③ 便利贴
（原始凭证）   →    （一条条事实）    →      （贴在额头上）
data/sessions/      history.jsonl            MEMORY.md
永远存全文           只追加，带编号            开机时拼进系统提示
    ↑                    ↑                        ↑
  已经有了          第 25/26 讲做了          第 24 讲做了读，
                                            第 27 讲做写（Dream）
```

**带着什么问题读**

- 便利贴（MEMORY.md）为什么放 `data/` 不放 `templates/`？（谁写 / 进不进 git / 缺了是不是错）
- 流水账的 `cursor` 是干什么的？和 `_summary.covered` 是同一个思路吗？
- 流水账的 `session` 字段为什么重要？
- 事实是**什么时候**被写进流水账的？为什么挂在压缩上？
- `append_fact` 的 `path` 参数默认值为什么是 `None` 而不是 `HISTORY_FILE`？

**四个标签 = 保质期**

| 标签 | 管多久 | 例子 |
|---|---|---|
| `permanent` | 一直 | 用户用 Windows、说中文 |
| `durable` | 几个月 | 项目用 Chroma、定下的架构 |
| `ephemeral` | 几周 | 当前在做阶段五 |
| `correction` | 推翻旧的 | "模型名是 X，不是 Y" |

**验证**：`python -m scripts.check_facts` —— 拿一段真实对话跑真模型，
看它提炼出什么。三件事要看：挑出来的是事实还是话题？标签对不对？有没有一条不该记的？

**已知的洞**（第 27 讲要补）：事实只在压缩时才写，而压缩的触发线是 190,000 token ——
整个项目所有 .py 加起来才 76,000。正常聊天几乎永远触发不了，
也就是说**记忆几乎永远不会被写**。nanobot 的主路径是"会话闲置 15 分钟就整理一次"，我们漏了这条。

### 第 8 步 · 测试：怎么读，以及负对照

`tests/` 下每个文件对应一层。**每个测试的 docstring 末尾都写了"负对照"**：
把代码改成那样，这个测试必须红。

读测试的方法不是从头看到尾，而是：

1. 读测试名，猜它在守什么
2. 读 docstring 里的负对照，**真的去改坏**，跑，看它红
3. 改回来，跑，看它绿

一个测试如果改坏了代码还是绿的，那它是假的安全感。项目里有过这种教训。

**两个一次性脚本**（不属于 Agent，项目里没有代码 import 它们）

| 脚本 | 干什么 | 什么时候跑 |
|---|---|---|
| `scripts/check_tokens.py` | 尺子 vs 真实 usage 对账 | 换模型、改系数之后 |
| `scripts/check_facts.py` | 调小触发线，看真模型提炼出什么事实 | 改了压缩提示词之后 |

都要用 `python -m scripts.xxx` 运行，不能 `python scripts\xxx.py`（否则找不到 `agent` 包）。

## 第二部分 · 设计说明：为什么是这样

### §1 分层规则表：每层知道什么、不知道什么

这张表是整个项目的骨架。每次加新东西，先想清楚它属于哪一行。

| 层 | 文件 | 知道什么 | **不知道**什么 |
|---|---|---|---|
| 编排 | `main.py` | 命令行、怎么打印、一轮的先后顺序 | 会话存在哪、循环转几圈 |
| 执行 | `agent/runner.py` | 怎么转循环、工具怎么执行 | `SOUL.md` 存在、在调哪家模型 |
| 上下文 | `agent/payload.py` | 怎么加工"这次要发的" | 谁会发它、发给谁 |
| 上下文 | `agent/compaction.py` | 摘要消息长什么样、切在哪 | jsonl 长什么样 |
| 上下文 | `agent/context.py` | 各层怎么排、怎么拼 | 记忆存在哪（只收到一段文本） |
| 模型 | `providers/base.py` | "调一次模型"长什么样 | 任何具体厂商 |
| 模型 | `providers/openai_compat.py` | 怎么把 SDK 返回翻译成统一形状 | messages 怎么攒出来的 |
| 存储 | `session/manager.py` | 会话有生命周期、带一条摘要记录 | jsonl 是什么、摘要消息什么格式 |
| 存储 | `session/messages.py` | 怎么读写 jsonl | "会话"是什么概念 |
| 存储 | `storage/jsonl.py` | 逐行读字典、跳过坏行 | 记录里有什么字段 |
| 工具 | `agent/tools/workspace.py` | 路径在不在围栏内、在不在禁区 | 文件存不存在 |
| 记忆 | `agent/memory.py` | MEMORY.md 和流水账在哪、怎么读写 | 系统提示长什么样、什么事值得记 |

**检验一个函数放对没放对的办法**：看它 import 了什么。
`runner.py` 里如果出现了 `from session import ...`，那就是放错了。

### §2 一条消息的旅程

以"读一下 runner.py"为例，跟着一条消息走完全程：

```
你敲的字
  │
  ├─ main.py           messages.append({"role":"user", ...})      ← 内存
  │
  ├─ runner.py 第1圈    build_payload(messages) → provider.chat()
  │                     模型说：我要调 read_file
  │                     messages.append(assistant, tool_calls=[...])
  │
  ├─ runner.py         tool.execute("agent/runner.py")
  │                     ↓ workspace.resolve() 先展开再判断
  │                     ↓ 读文件，返回全文 20,000 字
  │                     messages.append(tool, content=全文)        ← 存的是全文
  │
  ├─ runner.py 第2圈    build_payload(messages)
  │                     ↓ 那条 tool 消息在 payload 里被截到 4,000 字   ← 只改副本
  │                     → provider.chat()
  │                     模型说：它是主循环执行器。
  │                     messages.append(assistant, content="...")
  │                     没有 tool_calls → break
  │
  ├─ main.py           session.save_turn(messages[boundary:])
  │                     ↓ manager → messages.py → open("a") 追加
  │                     磁盘上 4 行：user / assistant / tool（全文）/ assistant
  │
  └─ main.py           print("AI > ...")
```

**同一条工具结果，三个地方三种形态**：

| | 内存 `messages` | 磁盘 jsonl | `payload` |
|---|---|---|---|
| 内容 | 全文 20,000 字 | 全文 20,000 字 | 截到 4,000 字 |
| 活多久 | 一次运行 | 永久 | 一圈 |
| 能不能改 | 能 | **只能追加** | 随便改 |

下一次启动、恢复这个会话，`restore_history()` 从磁盘读回全文，
然后每一圈 `build_payload` 再重新截一次。**截断阈值改了，历史立刻按新值生效。**

### §3 三份 messages 的区别（最容易绕晕的地方）

| 名字 | 在哪 | 谁生产 | 谁消费 | 里面有系统提示吗 | 里面有摘要消息吗 |
|---|---|---|---|---|---|
| 存档 | `data/sessions/*.jsonl` | `save_turn` | `resume` | ❌ 永不 | ❌ 只有 `_summary` 便条 |
| 内存 | `main.py` 里的 `messages` | `restore_history` + 每轮追加 | `runner` | ✅ 下标 0 | ✅ 压缩过就有，下标 1 |
| payload | `build_payload` 的返回值 | 每圈现造 | `provider.chat` | ✅ | ✅ |

**存档最干净**：只有真实发生过的对话（user / assistant / tool）。
系统提示每次启动重新拼，摘要每次启动重新造。
好处：改了 `SOUL.md`，所有历史会话下次加载都用新的；换了压缩策略，旧存档照样能用。

### §5 两道防线与阈值

| 常量 | 值 | 在哪 | 出处 |
|---|---|---|---|
| `MAX_TOOL_RESULT_CHARS` | 4,000 | `payload.py` | 单条上限，与总量无关 |
| `CLEAR_TRIGGER` | 100,000 | `payload.py` | Anthropic context editing 的 `trigger` 默认值 |
| `CLEAR_AT_LEAST` | 20,000 | `payload.py` | Anthropic 的 `clear_at_least`，避免频繁打断提示缓存 |
| `KEEP_TOOL_RESULTS` | 3 | `payload.py` | Anthropic 的 `keep` 默认值 |
| `CONTEXT_BUDGET` | 190,000 | `payload.py` | nanobot 公式；只占 1M 窗口的 19%，余量是为了**质量**不是怕装不下 |
| `KEEP_RECENT_RATIO` | 0.5 | `compaction.py` | 压缩时至少保留半个预算的原文 |
| `NO_WRITE_DIRS` | `("data",)` | `workspace.py` | 禁区 |
| `MAX_CONTENT_CHARS` | 4,000 | `memory.py` | 流水账单条上限，防模型把整段输入当摘要吐回来 |

**两个成本模型上的结论，都查过出处**（凭推理下过错结论，吃过亏）：

- "一次多清一点"是有收益的：`CLEAR_AT_LEAST` 就是为此存在的 —— 每清一次都会打断提示缓存，
  清得太勤反而更贵。
- `CONTEXT_BUDGET` 定在 19% 不是怕装不下，是模型在长上下文里质量会下降。

**一个还没解决的矛盾**：190,000 这条线是照 1M 窗口定的，但事实提炼挂在它上面，
导致记忆几乎不会被写（见第一部分第 7 步）。第 27 讲处理。

### §7 与 nanobot 的差异

不是功能等价实现，是为了理解其设计而做的重写。以下每条都核对过 nanobot 源码：

| 点 | nanobot | 本项目 | 理由 |
|---|---|---|---|
| 截断时机 | 执行工具时 | 发送前 `build_payload()` | 存档保真 |
| 压缩后保留多少原文 | 只保留还没发给模型的增量 | 最近半个预算的原文 | 摘要有损，最近的内容模型正在用 |
| token 估算 | `tiktoken` | 字符数 × 系数 | 拿 OpenAI 分词器数 DeepSeek 本来就是估算 |
| 会话文件头 | 无 | 首行 `_meta` | `--list` 只读一行 |
| 记忆写保护 | 提示词叮嘱 | 代码禁区 | 提示词是建议，代码是保证 |
| 摘要格式 | 整份都是 `- [标签] 事实` | 五项散文 + 末尾事实清单 | 我们的摘要还要负责"下一步""失败过的尝试" |
| 记忆触发 | 闲置 15 分钟 + 超预算 | 目前只有超预算 | **漏了主路径**，第 27 讲补 |
| 流水账编号 | 单独的 `.cursor` 计数器文件 | 每次扫全文取最大值 | 单进程，几百行扫一遍不值一提；先写死 |

**一处一致、但容易想当然的地方**：压缩**不改写存档**。nanobot 的 `set_summary_checkpoint`
注释写明 *"while preserving the transcript"* —— 它同样保留完整记录，只移动指针。
（README 早先写反了，核对源码后改正。）

### §8 负对照：测试怎么写才不是假的安全感

**教训**：有过测试全绿、把代码改回旧行为**照样全绿**的情况。那种测试守不住任何东西。

所以现在的规矩：

1. 写完测试，**先把代码改坏一遍**，确认测试真的会红
2. 改回来，确认绿
3. 把"改成什么样会红"写进测试的 docstring 末尾

例：

```python
def test_write_file_cannot_touch_memory(sandbox):
    """★ 不变量 6：主 Agent 不能改长期记忆。

    负对照：write_file 里把 resolve_for_write 改回 resolve → 变成成功回执。
    """
```

**doctest 的边界**：例子写成 `>>>` 格式可以被 `--doctest-modules` 验证。
但**碰文件系统的例子不要写成 doctest** —— doctest 的 `globals()` 是模块全局的拷贝，
隔离不了。那种放 `tests/` 里用 `tmp_path`。

**假 Provider**：凡是要调模型的路径，测试里用 `StubProvider` / `FakeProvider`
返回事先准备好的内容。慢、花钱、结果不稳定的东西不进 pytest；
那部分用 `scripts/` 下的一次性脚本手动验收。

### §9 已知短板与待办

**高优先级**

- [ ] 记忆触发线太高（190k），事实几乎不会被写。补"退出时/闲置时整理"（第 27 讲）
- [ ] `chat()` 无重试/超时，402/429/断网直接炸掉整个程序，丢掉用户那轮输入
- [ ] `save_turn` 在 `runner.run` 之后，中途崩溃丢整轮

**中优先级**

- [ ] `manager.create` 的 key 精度只到秒，同秒建两个会话会撞文件
- [ ] `write_file` 执行前没有用户确认（模型曾未经许可创建目录）
- [ ] 只有 `write_file`（整文件覆盖），没有 `edit_file`（精确替换）
- [ ] 截断说明报"字符"、`list_dir` 报"字节"，中文差 3 倍

**低优先级**

- [ ] 工具定义的 token 成本没计入预算
- [ ] 尺子漏掉约 790 的固定开销
- [ ] `list_all` 成本是「会话数 × 文件大小」
- [ ] `workspace.set_root(".")` 锚 cwd，其他模块锚 `__file__`，两套路径基准并存
- [ ] 阈值是模块常量，nanobot 里是配置项；等第二个场景再外化
- [ ] `load_meta` 只读第一行，meta 不在第一行就静默返回 None
